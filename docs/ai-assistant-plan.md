# Searchdesk AI assistant

Design record from 24 November 2026. The owner selected an assistant inside Searchdesk, with optional automatic analysis billed to the owner's AI API account. Questions and daily briefs have since shipped. For current setup and implementation, see the [README](../README.md) and [development handoff](HANDOFF.md).

## Product decision

Build one read-only assistant for the selected site. Start with the OpenAI Responses API in an installation controlled by the API account owner. Use the existing Rails web service, PostgreSQL and Solid Queue worker. The client signs into Searchdesk as usual. They can ask a question, inspect the facts behind an answer and opt into one daily brief.

**Who pays matters.** On the current Mac, the operator can use their own OpenAI project to pilot SkinHampshire. A client who owns a separate OpenAI account can run the same Docker deployment under their control. Treat a future agency-hosted deployment as a distinct credential arrangement. OpenAI documents project service accounts for scheduled workloads and restricts transfers of API keys to third parties. For a shared hosted service, qualify tenant-specific delegated access or a customer-controlled worker before offering client-paid OpenAI connections. [API keys and service accounts](https://developers.openai.com/api/docs/guides/api-keys) · [OpenAI Services Agreement, §3.3](https://openai.com/policies/services-agreement/) · [Workload identity federation](https://developers.openai.com/api/docs/guides/workload-identity-federation)

## What a business owner sees

1. **Integrations → AI assistant.** The owner chooses the billing project, connects a restricted credential on their own installation, and sets an allowance. Explain the provider's key-creation steps in the setup screen. Show which site, fields and people can use it. Offer a labelled, bounded test with synthetic text. Display “Ready”, “Credits exhausted”, “Budget reached” or “Reconnect” with the corresponding next action.
2. **Project brief.** Prefill the site, market, watchlist and preferred pages already held in Rails. Ask for services that matter most, business goals and the owner's definition of a useful enquiry. The owner can inspect the source, edit a business fact and see when it was confirmed. Additional source material enters through an explicit import or owner-approved excerpt.
3. **Rankings → Ask about this site.** Support plain-language questions and starters such as “What changed since tracking began?”, “Which page ranks for this keyword?” and “What should I check first?” Show the answer date, comparison period, source, device when applicable and clickable evidence. A saved answer opens with the site it describes. Short follow-ups carry only the allowed context from that site.
4. **Daily brief.** The owner enables it separately. Show up to three findings, any important gap in coverage and one next check per finding. Link to existing actions, de-duplicate the same issue across devices in the explanation, and retain the underlying device readings. The assistant can draft a recommendation. Website edits, extra paid searches and messages to customers require separate product workflows.

## What the assistant knows

The project record in PostgreSQL is the source of truth. Existing recipes in `config/seo_skills` cover deterministic keyword reviews and an optional Anthropic choice among approved wording lines. The latter's current permission covers those lines only. Use new, versioned question and daily-brief recipes. The backend selects and runs the relevant recipe. A new skill declares its allowed inputs, expected output and evidence tests before it can participate. [Current skill contracts](skills.md)

| Question | Evidence Rails supplies | Interpretation |
| --- | --- | --- |
| How have my rankings changed? | Comparable DataForSEO observations, first valid baseline, winning and preferred page, device, market and date. Semrush campaign history is a separately labelled series. | A first reading establishes a baseline. Preserve incomplete checks, verified outside-30 results and dated gaps. Compare like with like. |
| What work should I do next? | Open keyword actions and their evidence, preferred-page assignments, owner priorities and the current status of approved project tasks. | Link to the existing action. Distinguish a page mismatch worth reviewing from a confirmed site defect. |
| Are more people finding us? | Allowlisted Search Console performance, GA4 organic traffic and Local Falcon Maps observations, each with its own reporting period and source permissions. | Search Console supplies averages. Maps requires comparable grids. GA4 key events need validated definitions before they support qualified-enquiry claims. |
| What does the business want? | Owner-confirmed facts and selected project material with provenance and a revision date. | Ask about missing or conflicting facts. Prior ChatGPT conversations and files outside the project require explicit selection and import. |

Implement a site-scoped context builder with typed readers. Reuse `Tracking::Dashboard`, `SearchConsole::PositionDashboard`, `Semrush::CampaignDashboard`, `LocalFalcon::MapsSummary`, the verified analytics report and `SourceSnapshot.visible_for(site)`. Fetch only records relevant to the question. Rails computes counts, movements and comparable periods. Give the model compact evidence references and approved possible checks. Validate its structured reply, resolve references in Rails and render the values and links there. Treat imported material and questions as untrusted text. Constrain the first release to these read-only capabilities. [Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

For each source, record the allowed fields, sharing purpose, retention and required consent before enabling it. Preview those fields to the owner. Exclude credentials, private file paths, enquiry or patient details, raw analytics events and URL parameters. Send only authorized facts to the provider. In particular, a Google OAuth connection enables collection for its disclosed purpose. Check applicable Google scopes and give the owner a separate choice before sharing those derived metrics for AI analysis. A source with unresolved sharing rights can still appear in its existing dashboard. [Google API Services User Data Policy](https://developers.google.com/terms/api-services-user-data-policy)

## Rails implementation

| Work package | Deliverable | Acceptance |
| --- | --- | --- |
| 1. Project context | Editable site brief, versioned evidence schema, source readers and a preview. Use synthetic fixtures for the regression suite and the first client's private, dated records for the local pilot. | Source, date, scope and freshness survive serialization. A site switch, disconnected property or expired Maps record cannot expose data. This package runs without an AI account. |
| 2. Connection and budget | Workspace-owned provider connection, encrypted secret on the owner's deployment, per-site activation, manager permission, separate automatic-run consent and a shared allowance. Add a fixed HTTPS provider adapter to the Rails worker. | Owner can verify, rotate and revoke. A manager can ask only when delegated. A viewer can read authorized published briefs. No role can retrieve the saved key. Two workspaces have independent credentials and budgets. |
| 3. Ask Searchdesk | Local question and answer history, bounded conversation context, citation validation, and the assistant entry points on Rankings and Actions. Start with one evidence selection and one model request per answer. | First-day and incomplete observations produce accurate answers. Stale or absent evidence is labelled. Invalid references fall back to a local, factual result. A follow-up in one site cannot reuse another site's context. |
| 4. Daily analysis | Add an opt-in Solid Queue job using the same context, recipes and allowance. Schedule from the site's local reporting date after collection settles, with a cutoff for providers that are late. | At most one scheduled generation per site and report date. Late data stays labelled and becomes eligible for the next report. Retries, concurrent workers, a sleeping Mac and revoked consent cannot trigger duplicate charges or silently present an old brief as today's. |
| 5. Pilot | Run the Docker test suite with fake adapters, then exercise the owner and manager flows in a browser. Use one deliberately authorized, low-cost live request before activating the pilot schedule. | Reconcile the run receipt with provider usage, open its citations, and demonstrate disconnect, exhausted credits and model unavailability. Daily rankings and ordinary action reviews continue independently. |

Packages 1 and 2 can proceed in parallel after the context contract is agreed. The interactive answer path comes before automatic dispatch. Use the existing Rails image for web and jobs. PostgreSQL is sufficient for the initial structured questions and evidence. Reassess document search if owners begin adding long source collections.

### Spending, privacy and recovery

- Start with a zero allowance. Suggest **$1 per workspace per calendar month** in the setup flow and let the owner choose. Apply the cap across enabled sites, questions, tests and scheduled briefs. Record a durable reservation under a database lock before dispatch. Compute its upper bound using bounded input, maximum billable output including reasoning, and a versioned tariff for the selected service tier. Reconcile reported usage after completion. An uncertain post-dispatch outcome keeps its reservation and cannot trigger a duplicate paid request.
- Evaluate `gpt-6-luna` on the evidence fixtures first. At the published standard short-context price of $0.10 per million input tokens and $0.50 per million output tokens, 6,000 input and 1,000 billable output tokens cost **$0.0011**. At that size, 31 briefs and 100 questions cost approximately **$0.14** in model usage. This example assumes text only and standard processing. Refresh the tariff and evaluate quality before enabling a model. Searchdesk's cap controls calls made through Searchdesk. [Model capabilities and rates](https://developers.openai.com/api/docs/models/gpt-6-luna)
- Store the credential encrypted and filter it from Rails parameters, exception reports and job logs. Jobs carry a run ID. Check the workspace, site, membership or schedule grant, source permissions, budget and current connection revision again before sending. Keep the hosted-provider request in the worker with `store: false` and bounded timeouts. Explain that provider abuse-monitoring retention can still apply. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)
- Keep the site, requester, recipe and model version, usage, timestamps, approved evidence references and a digest of the selected facts with each run. Keep the authorized fact values needed to explain the answer for the allowed retention period. Recheck visibility at display time. On source expiry, deletion or withdrawal, hide or purge dependent saved answers and excerpts where required, including copies in follow-up context. Give the owner a history deletion control. Keep a minimal accounting receipt independent of sensitive content.
- Test a synthetic first collection of three keywords on two devices. Suppose four checks return numeric positions, one verifies the site outside the top 30 and one ends at 27 without a match. The correct answer reports five usable baselines and says a later comparable day is needed for movement. Two page-match actions for the same keyword on different devices count as two readings of one issue. Verify the same rules against the private 24 November pilot receipt. The assistant must answer “What should I check first?” without buying another SERP request.
